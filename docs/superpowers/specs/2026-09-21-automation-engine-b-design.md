# Automation engine, part B — more recipes

**Date:** 2026-09-21 · **Status:** drafted for danlo; the four recipes are his ("take all of your recommendations")
**Owner agents:** bis-automations (passes, gates, copy, cards), bis-db-schema (migration 0047, due-lists, grants tests), bis-comms (the inbound keyword leg)
**Supersedes nothing.** Obeys `2026-09-21-automation-engine-c-design.md` (quiet hours, `automation_log`, the release queue) and extends `2026-09-06-automations-design.md` (the harness) and `2026-09-07-automations-milestone-c-design.md`.

## Why this, and why now

C built the engine's shared floor: one quiet-hours window, one record, one queue. B is what the floor was built to carry. Four recipes, in priority order by the money they recover: a quoted lead that went quiet (`quote_followup`), a confirmation ask two days out (`appointment_confirm`), a customer nobody has spoken to in months (`reactivation`), and a referral ask that is not a review request (`referral_ask`). Each ships as a card with a toggle, writes `automation_log` from its first commit, and goes through `holdOrSend`.

## Verified facts (checked in the tree 2026-09-21 — do not re-derive)

- **The catalogue is four keys.** `RecipeKey = "review_request" | "no_show_nudge" | "sms_reminder" | "instant_reply"` (`packages/db/src/automations.ts:15`), mirrored by `automations_recipe_key_check`, which 0027 grew by drop-and-re-add (`0027_instant_reply.sql:28-30`). That is the shape 0047 copies.
- **`automation_log_source_check` allows exactly NINE values** — `reminders, followups, review_request, no_show_nudge, sms_reminder, instant_reply, weekly_report, concierge, voice` (`0046_automation_log.sql:35-37`), mirrored in `AUTOMATION_LOG_SOURCES` (`packages/db/src/automation-log.ts:10-13`). **It must grow to thirteen.** Two `Record<AutomationLogSource, …>` maps then fail to typecheck until the new keys are added — `RELEASERS` (`passes/release-held.ts:67`) and `SOURCE_TITLES` (`log-titles.ts:7`). That is the compiler doing the registry's bookkeeping; do not widen either to a partial.
- **Every due-list must go through `loadSendableRows`**, not `loadAccountBrandInfo` (`packages/db/src/booking.ts:501-521`), and `outbound-suppressed.test.ts:79-90` walks `booking.ts` and `automations.ts` and fails a `listDue*` that calls the latter directly. A contact-subject or opportunity-subject due-list still carries an `account_id` on every row, so it satisfies the `T extends { account_id: string }` constraint unchanged.
- **The release contract** (`passes/review-request.ts:267-280`): strip the prefix off `subject_key`, `getDueXById`, `logSkipped(… recipeOff | noLongerDue)` when it is gone, `if (found.due.accountId !== row.account_id) → skipped`, then `verdict(await processX(ctx, [found.due], { released: true }))`. `released` skips the morning BAND only; `holdOrSend` still runs.
- **A released row must never be left untouched** on a branch that can repeat, or it keeps its past `held_until` and parks the head of the queue forever (the part-C cleanup that produced `REASONS.smsCooldown`, `hold-or-send.ts:79-88`). Every `continue` in a new `processX` is classified: silent on a normal tick, a real `logSkipped` when `opts.released`.
- **Opportunities exist and are real** (`packages/db/src/opportunities.ts`, `0003_crm_core.sql:76-93`): `status in ('open','won','lost')`, `stage_id`, and **`stage_changed_at timestamptz not null default now()`**, written by both `moveOpportunityStage` and `moveOpportunityToStage` (`opportunities.ts:45-46, 65-66`). **What surprised me:** nothing creates an opportunity automatically — only the pipeline page's dialog and the demo seed (`grep createOpportunity`). The one semi-automatic path is a `call_proposals` row of kind `opportunity_stage` that the operator accepts (`packages/db/src/call-proposals.ts:3-13`). So the trigger is real but only fires for a client who works the board; that is a sales fact, not a schema gap, and the card's copy says so.
- **`pipeline_stages.name` is free text per account** (`0003_crm_core.sql:67-74`) and stages are blueprint-seeded (`blueprints.ts:398`). There is no platform-wide "Quoted" stage. The operator picks the stage by id.
- **`conversations` is one row per contact** with `last_message_at` (`0005_messaging.sql:11-25`, unique on `(account_id, contact_id)`), and `createMessage` touches it on every message from every writer — inbound SMS, booking actions, form enrichment, `finishCall`, and the automations' own sends (`messaging.ts:126-128`). **What surprised me:** that touch is deliberately best-effort and non-fatal (`messaging.ts:120-131`), so `last_message_at` can lag reality. It is a candidate filter here, never the final check.
- **There is no per-contact consent record.** `contacts.dnd jsonb` exists (`0003_crm_core.sql:13`) and is dead — the only `dnd` hits in the app are the `@dnd-kit` package. Consent is stored per form submission (`0006_forms.sql:48-52`), and the opt-out MECHANISM is Telnyx's carrier-side STOP list, not ours (`lib/sms/opt-out.ts:14-18`). This decides `reactivation`'s channel.
- **The inbound SMS webhook does no keyword handling at all** (`apps/web/src/app/api/sms/inbound/route.ts:95-174`): it drops self-texts from `accounts.alert_phone`, dedupes on `payload.id`, then `createContact` → `ensureConversation` → `createMessage` → `incrementUnreadCount`. Nothing reads the body. `handleInbound` is the only place a reply can be recognised.
- `bookings.status in ('booked','cancelled','completed','no_show')` (`0016_booking.sql:38-39`); the automation stamp columns were added by `0025:43` and `0026:33-39` as plain `alter table … add column`, with **no grant changes** (0027's header: new columns inherit the table's standing, pinned in `automations-grants.test.ts`).
- The gates compose from `followup-timing.ts`: `resolveAccountZone`, `isInMorningBand` (08:00–11:00), `isStrictlyEarlierLocalDay` (`:122, :155, :171`). `REVIEW_REQUEST_MAX_AGE_MS = 61h` is the follow-up's 37h plus one local day, and `cron-coupling.test.ts:51` pins that derivation.
- Caps today: `AUTOMATION_TICK_CAP = 10`, `AUTOMATION_DAILY_CAP = 25`, `DAILY_CAP_WINDOW_MS = 24h`, `SMS_RETRY_COOLDOWN_MS = 24h` (`caps.ts:15-41`), recipe passes only.

## Decisions taken in this design

1. **Four recipe keys, one migration, `0047_automations_b.sql`.** Rejected: one migration per recipe — the four share the two CHECK rewrites, and four drop/re-adds of the same constraint is four chances to spell the ninth value wrong.
2. **`appointment_confirm` is UNCAPPED**, the first recipe that is. The cap is a burst guard against a bug or a bulk status change (`caps.ts:6-13`); this pass is keyed on `starts_at` in a 75-minute window, so no status change and no import can burst it, and a fully-booked Saturday would otherwise leave five customers unasked. `caps.ts`'s doc comment grows to name it. Rejected: capping it for consistency — consistency that drops a real customer's text is not a rule worth keeping.
3. **`reactivation` gets its OWN cap, `REACTIVATION_DAILY_CAP = 5`**, and sends at most once per contact EVER. Rejected: reusing the 25/day cap — 25 a day is 750 people a month who did not just interact with the business, which is a blast.
4. **`reactivation` is email-only in v1.** There is no per-contact SMS consent in this schema (verified above), and a "we haven't seen you in a while" text is marketing, not customer care, against an A2P campaign that does not exist yet. The unlock is named, not vague: a per-contact consent column (0048) plus an approved marketing campaign. Rejected: an SMS option behind a warning — a warning is not consent.
5. **A NO reply never cancels a booking.** It records the answer and raises the unread count; the operator cancels. A destructive action from one word in a text, with no confirmation, is exactly what DESIGN.md rule 6 forbids.
6. **A YES gets no text back, and the ASK carries the reassurance instead** (danlo, 2026-09-21). A second outbound per confirmation costs a message, risks a loop against the carrier's own STOP handling, and would make the webhook a sender rather than a recorder. But a customer who replies YES into silence does not know it worked, and this recipe exists to cut no-shows, so certainty matters — so the certainty is written into the ask, not bought with another send: "either way we'll see it". The operator sees the confirmation on the booking. Rejected: an inline ack through `sendInstantReply`'s path. A reply-back is a LATER DECISION, not a gap.
7. **`referral_ask` is the ladder's third rung** and defers to the review request explicitly, not by luck. Rejected: making it a channel option on `review_request` — one row cannot be enabled twice with two bodies, and an operator who wanted only referrals would have to turn reviews off.
8. **Every new recipe's channel choice is a config field with NO silent fallback**, the `review_request` rule (`passes/review-request.ts:131-133`): a refused SMS gate skips and logs, it does not become an email.
9. **`reactivation`'s quiet period is 9 months, configurable 6–18** (danlo, 2026-09-21). Roofing and landscaping are seasonal: nine months reaches someone whose last job was last spring, while the relationship is still warm enough that the message reads as a business they know. Rejected: twelve months — a full cycle, by which point it reads as a blast from a stranger, which is precisely the risk this recipe carries. The range is narrowed to 6–18 for the same reason: three months is too soon to call someone lapsed, two years is a cold list.
10. **Build order is not priority order** — see the section below. The ranking danlo gave is by revenue ceiling; the build order is by how certainly each recipe fires, and this spec's own pipeline finding moves `quote_followup` last.

## Recipe 1 — `quote_followup`

- **Trigger.** An `opportunities` row the operator parked in the stage they nominate. Due-list predicates, all on real columns: `status = 'open'`, `stage_id = config.stageId`, `quote_followup_sent_at is null`, `stage_changed_at <= now - config.quietDays` and `stage_changed_at >= now - QUOTE_FOLLOWUP_MAX_AGE_MS` (30 days — a 7 AM text about a month-old quote reads as a mistake), account in `listEnabled("quote_followup")`, then `loadSendableRows`. **Then the quiet test, which the query cannot express:** for the surviving candidates only, one read of `messages` through `conversations` for `direction = 'inbound'` and `created_at > stage_changed_at`; any hit drops the row. Candidates are bounded by `QUOTE_FOLLOWUP_CANDIDATE_LIMIT` (200, oldest stage change first), so this is one bounded `.in(…)` read per tick, not one per row; the tick cap is a SEND cap applied later in the pass and bounds nothing about this read.
- **Why not something simpler.** The pipeline can express it, so nothing is invented. The honest caveat is above: it only fires for a client who moves cards, and the card's copy says "This watches your pipeline. It only runs for deals you move into the stage you pick."
- **Channel:** configured, `sms` or `email`. **Gate:** morning band 08:00–11:00 plus the stage-quiet test; no band exemption. **Cap:** `AUTOMATION_TICK_CAP` + `AUTOMATION_DAILY_CAP`, plus `SMS_RETRY_COOLDOWN_MS` read back off `quote_followup_sms_failed_at`, the `review_request` shape.
- **Copy** (`quote-followup-copy.ts`): one line, the brand name, no price and no deal name — the deal's `name` is the operator's internal words ("Smith reroof — maybe"), the same class of leak `accounts.name` is. Default: "Hi, it's {name}. Just checking you got the quote we sent — happy to answer anything or adjust it. Any questions?"
- **Operator configures:** on/off, the pipeline stage (a select of that account's `pipeline_stages`, stored as `stageId`), days quiet (default 3, range 1–30), channel, body. A `stageId` that no longer belongs to the account skips with a new reason, "The stage this automation watches is gone".
- **`subject_key`:** `opportunity:<id>`, source `quote_followup`. **Stamp:** `opportunities.quote_followup_sent_at`; one send per opportunity, ever.
- **`releaseQuoteFollowup`** re-reads by opportunity id and re-checks: recipe still on, `status` still `open`, `stage_id` still the configured one, still unstamped, `found.due.accountId === row.account_id`, **and the inbound-quiet test again** — a customer who replied during the hold must not be chased at 8 AM. Then `processQuoteFollowups(ctx, [due], { released: true })`.
- **Off:** the card's toggle; `accounts.outbound_suppressed`; or clearing the stage.

## Recipe 2 — `appointment_confirm`

- **Trigger.** `bookings` with `status = 'booked'`, `confirm_asked_at is null`, and `starts_at` inside `[now + APPOINTMENT_CONFIRM_WINDOW_START_MS, now + APPOINTMENT_CONFIRM_WINDOW_END_MS]` = `[47h, 48h15m]` — 75 minutes, the email reminder's width and for its reason (`booking.ts:383-384`). **`cron-coupling.test.ts` grows a case** pinning this third window against `vercel.json`; change one, change both.
- **Channel: SMS only.** "Reply YES" is a text idiom; in an email it points at a no-reply address. No email option, so no channel config field. No textable phone, or a refused gate, skips and logs.
- **Gate:** the window alone. No morning band: the window is relative to `starts_at`, and quiet hours already holds a 6 AM send until 08:00. **`deadline` on the `HoldSubject` = `starts_at − 24h`** — the instant the ask stops being useful, because the email reminder is about to go. `holdOrSend`'s existing exemption then sends early rather than holding past usefulness (`hold-or-send.ts:59-63`).
- **Cap:** none (decision 2). `SMS_RETRY_COOLDOWN_MS` is NOT read back either — the window is 75 minutes, so a 24h hold would mean one attempt ever, the exact bug the text reminder's exemption records (`caps.ts:34-40`). The marker is still written.
- **Copy** (`appointment-confirm-copy.ts`), carrying the reassurance decision 6 refused to buy with a second send: "Hi, it's {name}. You're booked for {when}. Reply YES to confirm or NO if you need a different time — either way we'll see it." `{when}` through the formatter the SMS reminder already uses, in the account's zone, plus `withOptOut`. A copy test asserts the "either way" clause is present: it is the whole reason there is no reply-back.
- **The reply, and exactly what changes.** `handleInbound` gets ONE new leg after `incrementUnreadCount`, in its own try/catch — the `getAlertPhone` pattern (`route.ts:126-131`), because a keyword failure must never discard a customer's message: `await applyConfirmationReply(db, accountId, contact.id, payload?.text ?? "")`. That function is pure matching plus one update. It lowercases, trims, strips trailing punctuation and matches a WHOLE word from `{yes, y, si, sí, confirm, confirmed}` → `yes` and `{no, n, cancel}` → `no`; anything else does nothing at all (a message that merely contains "no" is not a NO). It then finds that contact's MOST RECENTLY ASKED unanswered booking — `status = 'booked'`, `confirm_asked_at is not null`, `confirm_reply is null`, `starts_at > now()`, `order by confirm_asked_at desc` (with `starts_at` ascending as the tiebreak for two asks stamped in the same millisecond), `limit 1` — and writes `confirm_reply` and `confirm_reply_at`. Most recently asked, because the customer is answering a TEXT, and the text they are holding named one particular day and time: two booked jobs less than 48h apart are asked about on consecutive days, both asks are outstanding when the second is answered, and ordering by `starts_at` puts Sunday's "NO" on Saturday's job. (Amendment B12 shipped `starts_at` ascending; audit B's I2 found that case and it is reverted to this line — see B12's own postscript.) No status change, no send (decisions 5 and 6). The booking drawer and the work queue show the answer.
- **`subject_key`:** `booking:<id>`, source `appointment_confirm` — it does not collide with `sms_reminder`'s identical subject key, because the log's unique key is `(account_id, source, subject_key)` (`0046:53`).
- **`releaseAppointmentConfirm`** re-reads the booking: still `booked`, still unstamped, recipe on, account matches, **and `starts_at > now + 24h`** — a confirm released after a long hold, now inside the reminder's own lead, is `skipped` with a new reason, "Too close to the appointment to ask".
- **Off:** the toggle; suppression; the account losing its texting gate.

## Recipe 3 — `reactivation`

- **Trigger.** A past CUSTOMER who has gone quiet — not a list. Predicates: account in `listEnabled("reactivation")`; `contacts.reactivation_sent_at is null`; `contacts.email is not null`; the contact's `conversations.last_message_at <= now - config.months` (default 9, range 6–18 — decision 9); **and at least one `bookings` row for that contact with `status = 'completed'`** — this is the rule that stops it being a blast, and it is a query predicate, not a hope. Ordered by `last_message_at` ascending so the five a day drain oldest-first and nobody starves. Then `loadSendableRows`. Before sending, the lagging-touch guard: re-read the contact's newest `messages.created_at` and drop the row if it is inside the cutoff (verified fact: the conversation touch is best-effort).
- **Channel: email** (decision 4). **Gate:** morning band 08:00–11:00, plus quiet hours. **Cap:** `REACTIVATION_DAILY_CAP = 5` per account per 24h, a new constant in `caps.ts` counted off `reactivation_sent_at`; plus once per contact ever.
- **Copy** (`reactivation-copy.ts`): no urgency, no discount, no "we miss you". Default: "Hi, it's {name}. It's been a while since we were out at your place. If anything needs looking at before the season, just reply and we'll get you on the schedule." Subject line plain, the brand name, no exclamation mark.
- **Operator configures:** on/off, months quiet (6–18, default 9), body. Nothing else — a segment picker is the rule builder danlo deferred.
- **`subject_key`:** `contact:<id>`, source `reactivation`. **Stamp:** `contacts.reactivation_sent_at`.
- **`releaseReactivation`** re-reads the contact and re-checks **the quiet test first**: someone who wrote in during the hold must never receive "it's been a while". Plus unstamped, email still present, recipe on, `found.due.accountId === row.account_id`.
- **Off:** the toggle stops it mid-drain and strands nothing, because the stamp is per contact and permanent.

## Recipe 4 — `referral_ask`

- **Trigger.** A completed booking, anchored on `laterOf(ends_at, completed_at)` (`anchor.ts`, 0026's clock) — the review request's own trigger, one rung later.
- **The ladder, and why it cannot collide.** Follow-up day 1 → review request day 2 → referral ask day 3. `shouldSendReferralAskNow(now, anchor, followupSentAt, reviewRequestedAt, reviewRequestEnabled, timezone)` composes the same predicates: inside `REFERRAL_ASK_MAX_AGE_MS = 85h` (61h plus one local day, the derivation `cron-coupling.test.ts:51` already pins for the review request, extended one rung and pinned the same way); morning band; anchor on a strictly earlier local day; and `isStrictlyEarlierLocalDay` for BOTH `followup_sent_at` and `review_requested_at` when set. **Plus the precedence rule:** when `review_request` is enabled for the account, `review_requested_at` is null and the anchor is still inside 61h, the referral ask waits — so the review always goes first, never merely usually. `listDueReferralAsks` reads `listEnabled("review_request")` as a second narrow map to answer it.
- **Distinct from the review request by content, enforced:** it asks for a NAME, never a rating, and `config` has no `reviewUrl` field to put a link in. A copy test asserts the body contains no `http`.
- **Channel:** configured, `sms` or `email`. **Cap:** `AUTOMATION_TICK_CAP` + `AUTOMATION_DAILY_CAP`, and `SMS_RETRY_COOLDOWN_MS` off `referral_ask_sms_failed_at`.
- **Copy** (`referral-ask-copy.ts`): "Thanks again from {name}. If you know someone who needs the same done, reply with their name and number and we'll look after them."
- **`subject_key`:** `booking:<id>`, source `referral_ask`. **Stamp:** `bookings.referral_asked_at`.
- **`releaseReferralAsk`** re-reads the booking: still `completed`, still unstamped, recipe on, account matches, and the precedence rule re-applied — if the review request is still owed, the released row is written `skipped` with the reason "Waiting for the review request to go first" rather than left untouched (the parked-row rule), and the normal pass re-discovers the unstamped booking the next morning, moving the same log row back to `held` or `sent` in place.
- **Off:** the toggle; suppression.

## Testing (every claim is a mutation that must go red)

- **Gates, pure and alone.** `quote-followup-gate`, `appointment-confirm-gate`, `reactivation-gate`, `referral-ask-gate`. Boundaries tested AT the boundary, one millisecond either side — the negative fixture for "85 hours is too stale" is 85h + 1ms, never "a week ago", which passes against any ceiling and is the too-far-negative shape. Mutation for each ceiling: change the constant by one hour and the boundary pair fails by name.
- **The ladder's collision, the one that matters.** A booking whose `review_requested_at` is this morning gets no referral ask this morning and does the next. Mutation: delete the `review_requested_at` clause in `shouldSendReferralAskNow` → the same-morning case goes red. Second mutation, for the precedence rule: make `reviewRequestEnabled` unread → the "review request still owed" case goes red. Neither fixture may share a value with the follow-up's stamp: a fixture where `followup_sent_at` and `review_requested_at` are the same instant is satisfied by whichever clause survives, which is the fixture-equal shape.
- **Reactivation's anti-blast rule.** A contact with no completed booking, quiet for two years, with an email, is NOT due. Mutation: drop the completed-booking predicate → that case goes red. And the cap: with six eligible contacts, exactly five send and the sixth is `skippedCap` — asserting `5`, not "at least one", and the fixture holds six so the assertion cannot be satisfied by the tick cap of 10.
- **The quiet re-check on release**, for `quote_followup` and `reactivation`: an inbound message written DURING the hold makes the release `skipped`, not `sent`. Mutation: remove the re-check from the releaser → red. This is the test that keeps a release from being a replay.
- **`applyConfirmationReply`,** as a pure matcher plus one integration case: "YES", "yes.", "Si", "sí" and "no" match; "yes please, but move it to Friday" and "I said no problem" do NOT (whole word, not substring). Mutation: swap the whole-word match for `includes()` → both negatives go red. A second case: a reply with no pending ask writes nothing; a reply after the appointment started writes nothing.
- **Tenancy on every releaser:** a held row whose `account_id` differs from the re-read subject's never sends. Mutation: delete the `found.due.accountId === row.account_id` line → red, four times.
- **`outbound-suppressed.test.ts` gets its four cases written BEFORE the four due-lists** (the standing rule), and the static walk already fails a due-list that reaches for `loadAccountBrandInfo`.
- **Copy:** each `*-copy.ts` gets the `INTERNAL_MILESTONE` guard and a no-`{{`-syntax assertion; `referral-ask-copy` additionally asserts no `http`. Mutation for that one: paste the review URL into the default body → red.
- **The registry and the log:** `PASSES` contains the four new passes in order; `RELEASERS` and `SOURCE_TITLES` are exhaustive by type, so the mutation is deleting a key and watching `pnpm --filter web typecheck` fail — a type error IS the red here, and the report pastes it.
- **`cron-coupling.test.ts`** grows the `appointment_confirm` window case. Mutation: move the window start to 46h without touching `vercel.json` → red.
- **Vacuity watch, named:** no test asserts a counter's total where the interesting number is a single field (`skippedCap` is asserted by name, not as "some skip happened"); no `-t` filter is used on a name that does not exist; no negative fixture sits more than one unit past a boundary.

## Build order (not the priority order, and why)

danlo's ranking is by revenue ceiling. Build order is by how certainly a recipe FIRES, because a recipe that never fires teaches us nothing and a recipe that fires on day one is where the engine's new seams get proven. **`appointment_confirm` → `referral_ask` → `reactivation` → `quote_followup`.** `appointment_confirm` is first because it fires on every booking a client already takes — no new operator habit — and it exercises the two seams nothing has exercised yet (a `deadline` on the `HoldSubject`, and a write into the inbound webhook), so its bugs surface while the branch is small. `referral_ask` is second because it rides the completed-booking ladder the review request already walks: the anchor, the band, the stamps and the cap accounting all exist, so it is mostly a gate and a copy file, and it gives the log a second `booking:<id>` source that proves the unique key really is `(account, source, subject)`. `reactivation` is third: its machinery is new (a contact subject, its own cap, a due-list that is not booking-shaped) and it is the one with spam teeth, so it wants a quiet branch and unhurried review. `quote_followup` is last despite the highest ceiling, and this spec's own finding is the reason — nothing creates an opportunity automatically, so its trigger is conditional on a client working the pipeline board, and shipping it before anyone does is shipping a recipe with no evidence it ever ran. That sequencing risk is worth naming now rather than discovering in the ledger.

## Out of scope, recorded

Re-arming `quote_followup` when an opportunity re-enters the stage (v1 sends once per opportunity, ever). A segment picker or any audience builder for `reactivation` — that is the rule builder, deferred. SMS for `reactivation` until a per-contact consent column and a marketing campaign exist. Auto-cancelling on NO. **A text back after a YES or a NO — a later decision, not a gap** (decision 6): the ask's own "either way we'll see it" is what covers the customer until that decision is taken, and taking it would cost one inline send through the instant reply's existing path plus one more `automation_log` source. Per-account caps and dollar cost (C's out-of-scope, unchanged). A second scheduler for any of it — every "delay" here is a stamp plus a window plus the next tick.

## Amendments taken from the plan (2026-09-21)

The plan (`docs/superpowers/plans/2026-09-21-automation-engine-b.md`) is authoritative over this body wherever they disagree. Its amendment list, verbatim:

- **B1. `AUTOMATION_LOG_SOURCES` grows ONE source per recipe task, not all four alongside the migration.** The spec's migration section says the constant grows "in lockstep" with the CHECK. It cannot usefully: the instant a source is added, `RELEASERS` (`passes/release-held.ts:67`) and `SOURCE_TITLES` (`log-titles.ts:7`) stop compiling, and that red is the registry's bookkeeping. Adding all four at once produces four simultaneous errors an implementer can silence with three `null`s and one real releaser — the exact half-registration the type is there to prevent. Adding one at a time makes the red arrive in the same commit as the releaser and the title that answer it, four times. The SQL CHECK still grows to thirteen in one migration (spec decision 1): a TS constant NARROWER than the database's CHECK is safe in the only direction that matters — nothing can write a source Postgres would reject.
- **B2. `RecipeKey` grows the same way**, one key per recipe's data-layer task, for the same reason and to keep Task 1's diff to one `.sql` file and one test file a reviewer can reject on its own.
- **B3. A vanished `stageId` cannot be logged on a normal tick.** The spec says it "skips with a new reason". It cannot: the due-list filters on `stage_id`, so a vanished stage produces no row, and an `automation_log` write needs a subject with a channel (`review-request.ts:83-86` makes the identical argument for an invalid config — console only, no row). So `REASONS.stageGone` is written by `releaseQuoteFollowup` (a held row whose stage vanished during the hold — a real, reachable case) and the operator-facing warning lives on the card, which can see the account's stages.
- **B4. The `appointment_confirm` reassurance lives in the LEAD, not the operator's body.** Decision 6 buys certainty with the ask's own words; if "either way we'll see it" sat in an editable body, the copy test asserting it would assert a default the operator can delete. So the recipe follows `smsReminderLead` (`sms-reminder-copy.ts:10-15`, composed by `composeSmsReminder` at `:27-29`): a fixed lead the operator cannot rearrange, plus an optional closing line.
- **B5. `listDueReactivations` pushes every predicate it CAN into the candidate query, and walks pages for the one it cannot.** The contact predicates — unstamped, has an email — ride a `contacts!inner(...)` embed (`booking.ts:638`, `:663` is the precedent). Two things stay client-side and neither is negotiable: `months` is PER-ACCOUNT config, so one query cannot carry four different cutoffs (the widest goes to Postgres, each row is narrowed to its own), and "has a completed booking" has no path from `conversations` to `bookings`. Because that second one is a permanent disqualifier for a LEAD, a single 200-row page would let an account's oldest lead conversations park the window for ever — so the read walks up to `REACTIVATION_CANDIDATE_PAGES` pages until `REACTIVATION_SURVIVOR_TARGET` rows survive. The quiet period is then re-checked EXACTLY, per row, in the pass.
- **B6. Two hunks land in `bis-booking`'s files** — `BookingRow.confirm_reply`/`confirm_reply_at` in `packages/db/src/booking.ts` (`BookingRow` (anchor on the symbol, not a line), `BOOKING_COLS` (anchor on the symbol, not a line)) and one badge in `calendar/bookings-list.tsx`. So `apps/web/src/lib/email/templates/{referral-ask,reactivation,quote-followup}.ts` are created. `bis-comms` owns the shell and the rules; this plan writes only content and each file reuses `shell()` + `escapeHtml()` exactly as `bookingFollowupEmail` does (`followup.ts:44-47`) — no new shell primitive, no button in any of the three, because in all three the action is "reply to this email" and a button would need somewhere to point.
- **B8. The `INTERNAL_MILESTONE` guard already covers every new message key.** The spec asks each `*-copy.ts` for its own guard test. `apps/web/src/lib/messages.test.ts:44-51` already walks EVERY key in the catalogue and fails any that matches `/\bM\d[a-z]?\b/`, with a named `AGENCY_ONLY` allowlist that a second test keeps from rotting. That is strictly stronger than a per-module assertion, and every key this plan adds is covered by it the moment it is added. The per-copy tests in Tasks 3, 6, 8 and 10 keep their own assertion anyway — they check the COMPOSED string, not just the catalogue entry — but **no implementer adds anything to `AGENCY_ONLY`**: every string in part B is customer-facing.
- **B9. `listDueQuoteFollowups` is bounded by its own candidate limit, not by the tick cap.** The spec (line 42) says "Candidates are bounded by the tick cap". They are not: `AUTOMATION_TICK_CAP` is applied inside `processQuoteFollowups`, after the read. This recipe's trigger is a RESTING state with a thirty-day window, so an account whose nominated stage holds hundreds of open deals would put hundreds of uuids into the quiet test's `.in(…)` and fail the whole tick for every account. So `QUOTE_FOLLOWUP_CANDIDATE_LIMIT = 200` (oldest stage change first) bounds the due-list, mirroring `REACTIVATION_CANDIDATE_LIMIT`, and the thirty-day ceiling — not the ordering — is what drains the head of that queue.
- **B10. `0047` ships NINE indexes, not the five the spec’s shape implied, and one the first draft named is dropped.** Three are the cap counts, one per CAPPED recipe — and `appointment_confirm` is not one of them, so `bookings_confirm_asked` is gone: it would index a column nothing ever counts (the recipe is uncapped by decision 2, and this plan deliberately declares no `countAppointmentConfirmsSince`), while `countQuoteFollowupsSince` would have had a sequential scan on `opportunities` every tick. The NINTH was added by the pre-apply review: `applyConfirmationReply` (Task 4) looks a booking up by `(account_id, contact_id)` with `confirm_asked_at is not null and confirm_reply is null and starts_at > now()`, on the hot path of every inbound text from a known contact, and neither `bookings_confirm_due` (whose `confirm_asked_at IS NULL` is that query’s exact contradiction) nor `bookings_completed_by_contact` (whose `status = 'completed'` the query does not imply) can serve it — so `bookings_confirm_reply_pending` does. - **B11. `APPOINTMENT_CONFIRM_MIN_LEAD_MS` is the email reminder's window END (24h15m), not the spec's flat 24h.** The spec's reason is right and its number is not: the email reminder's due window is `starts_at ∈ [now + REMINDER_WINDOW_START_MS, now + REMINDER_WINDOW_END_MS]` = `[23h, 24h15m]` (`booking.ts:383-384`, used at `:546-547`), so a booking becomes eligible for the reminder the first tick at which its lead is **24h15m** — the window's CLOSE is where the reminder OPENS. A 24h lead therefore leaves a 15-minute band in which a released confirmation ask and the email reminder are both due. The constant is `(24 * 60 + 15) * 60 * 1000`, declared as its own literal (the `REVIEW_REQUEST_MAX_AGE_MS = 61h` shape, `automations.ts:158`) with `cron-coupling.test.ts` pinning it against `REMINDER_WINDOW_END_MS` — derived from the import it could never drift, and a coupling assertion that cannot fail is not a coupling assertion. **The collision is ONE TEXT AND ONE EMAIL**, not "two texts": the SMS reminder's window is 90–135 minutes (`automations.ts:466-467`) and cannot meet a 24h lead at all. Every comment that said "two texts and one confused customer" says the true thing instead.
- **B12. The confirmation-reply lookup takes the SOONEST UPCOMING unanswered ask, not the spec's "most recent".** Spec Recipe 2 says "that contact's single most recent booking with `confirm_asked_at is not null`". The appointment a customer has in mind when they text YES is the next one, not the one they were asked about last, and an appointment that has already started is not a thing anyone is confirming — so the query orders `starts_at` ASCENDING behind `.gt("starts_at", now)`. With one outstanding ask the two rules agree; they differ only when a contact has two, which is exactly when getting it wrong writes the answer on the wrong job. **REVERTED 2026-09-22 by audit B's I2 — this amendment was wrong.** It reasoned about which appointment the customer has in mind and forgot which TEXT they are holding: the ask names `formatWhen(startsAt, zone)` for one specific booking, so with two asks outstanding (a two-day job, or a morning slot plus a next-day slot, asked about on consecutive days) the soonest is precisely the one they are NOT answering — the calendar then reads "Asked for a different time" against Saturday while Sunday reads as unanswered. `applyConfirmationReply` orders `confirm_asked_at` DESC, with `starts_at` ascending as the millisecond tiebreak; `.gt("starts_at", now)` and `.eq("status", "booked")` are unchanged and still do their own work. The spec's Recipe 2 line, which said "most recent" from the start, stands as written. `bookings_confirm_reply_pending` is `(account_id, contact_id, starts_at)` and so no longer supplies the ORDER (it still supplies the equalities and the partial predicate); the plan sorts the handful of rows one contact's two equalities return, which is the trade this reversal buys and 0047 needs no change for.
- **B13. `{when}` in the confirmation text renders in the BOOKER's zone, not the spec's "the account's zone".** The spec sentence points at "the formatter the SMS reminder already uses" and that formatter is called `safeZone(row.bookerTimezone ?? undefined, row.accountTimezone)` (`passes/sms-reminder.ts:115`, the email reminder's rule) — the precedent the spec cites contradicts the zone the spec names. There is no booking drawer in this app — `…/[accountId]/calendar/` holds `bookings-list.tsx`, `calendar-settings.tsx`, `embed-snippet.tsx`, `hours-form.ts`, `actions.ts` and `page.tsx`, and nothing else. So Task 4 ships the one surface that is both real and timely: the badge on the calendar's bookings list.
- **B15. The confirmation-reply lookup is scoped to STILL-BOOKED bookings, and its UPDATE reports what it matched.** The spec lists the reply predicates (`2026-09-21-automation-engine-b-design.md:57`) as account, contact, `confirm_asked_at is not null`, `confirm_reply is null` and upcoming — no status. That is a live bug, not a tidiness point: a contact with an asked booking at +47h that was then cancelled through the cancel link, and a second asked booking at +71h, sends one "YES" and the answer lands on the CANCELLED one, because it is the sooner and B12 takes the soonest. Task 4's badge would then paint "confirmed" on a job nobody is doing while the live appointment reads as unanswered. So the lookup carries `.eq("status", "booked")`, proven by `applyConfirmationReply never answers a CANCELLED booking, even when it is the most recently asked` in `automations.test.ts` (the cancelled fixture WINS THE ORDERING on purpose — behind the live one the order would exclude it anyway and the filter would be non-load-bearing; since B12's reversal that means an explicit `confirm_asked_at` more recent than the live booking's, not merely an earlier `starts_at`). `bookings_confirm_reply_pending` still serves the read: an equality on a column the index does not carry is a recheck of the rows it returned, not a lost index, so 0047 needs nothing. Second half: the UPDATE's `.is("confirm_reply", null)` is a compare-and-set whose only possible loser is a second inbound text arriving between the SELECT and the UPDATE, and without a `.select()` the function could not tell a matched write from a lost race — it returned the answer either way, while its own doc comment promised "the answer it wrote, or null when it wrote nothing" and Task 4's route logs on exactly that value. It is now `.select("id").maybeSingle()` with `return written ? answer : null`. **No mutation can red that CAS predicate** (the SELECT already excludes answered rows, so single-threaded it always matches) and the code says so in place, rather than leaving it looking like a filter a later author should be able to prove; dropping the `.select()` DOES red two cases, which is what keeps the guarded return honest.
