## 3. The design

### 3.1 One module, two audiences

New folder `apps/web/src/lib/tools/`:

- `belt.ts`: the transport-neutral types and helpers, no handlers.
  - `ToolSpec<A extends Audience>`: `{ audience: A; name; description; parameters }` where
    `Audience = "customer" | "staff"`. `parameters` is a JSON-schema object.
  - `realtimeShape(spec)`: the flat GA Realtime format both voice sessions send today, byte-identical to the current
    literals INCLUDING key order and array order. Today's tests do not pin whole objects (`schemas.test.ts` checks
    names, one description and parameter keys; owner `session-config.test.ts:17` checks names), so PR 1 and PR 2 each
    capture the current output into a fixture from main first. Specs stay `as const` so derived name types
    (`OwnerToolName`, `ToolName`) stay narrow.
  - `chatShape(spec)`: the gateway's `AiTool`.
  - `runOffered({ catalogue, offered, name, args, run, notOffered, unknown, onError })`: the ONE guard every runner goes
    through. Order: a name not in this audience's catalogue → `unknown`; a known name not on THIS session's offered
    list → `notOffered(name)` (the assistant's own refusal words); otherwise `run`; a throw → `onError(errorClass)`,
    which logs the error's CLASS, never its message (the owner line's rule, `owner-line/tools/registry.ts:9`).
  - `errorClass(e)`, moved here from the owner line.
- `customer/specs.ts`: every customer-audience spec. `staff/specs.ts`: every staff-audience spec.
- The two catalogues share no name (a test). A session is built from ONE audience's catalogue by type: a staff spec
  cannot be put on a customer session (owner-line spec §4.4, today a comment in `owner-line/tools/schemas.ts:2`).

### 3.2 Variants, not duplicates

Some tools change their contract with the session: `book_appointment` on a video calendar (`VIDEO_BOOK_TOOL`),
`check_availability` under "Always take a message", and `capture_lead`, whose web schema is flat and whose phone
schema takes `fields`. A spec may carry `variants` keyed by a session fact; the selector picks one per session.
Each name still has ONE entry in the catalogue, so "which tools exist" has one answer. Unifying the two
`capture_lead` schemas would change what both models are asked to fill, so it is NOT done here (D1's spirit).

### 3.3 Handlers stay where they are

The belt owns names, contracts, selection and the guard. It does not move handler bodies:

- Phone: `runTool`'s switch keeps its cases; its entry runs through `runOffered`. Today there are TWO not-offered
  refusals with different words: the mode refusals at registry.ts:315-326 (`book_appointment` off "full";
  `MANAGE_TOOLS`, registry.ts:88, with booking off) and `transfer_to_human`'s own refusal inside its case
  (registry.ts:979-986) when no handoff target exists; `capture_lead`, `take_message` and `log_transcript` are never
  refused. The phone's `notOffered(name)` is a per-tool table returning exactly those sentences, and the
  `transfer_to_human` case keeps its own refusal too (it also covers a missing call row). A model that calls a tool
  it was not given hears exactly what it hears now. (The guard's transfer refusal and the case's say the same words
  and the case checks the target first, so the two cannot be told apart from outside; that is intended.) The `default: throw` stays as the unreachable last resort.
- Owner line: `runOwnerTool` keeps the live re-check; the three reads move to `lib/tools/staff/` and take a
  `StaffReadContext` (`{ db, accountId, timezone, locale, now }`, the `c` object at `owner-line/tools/registry.ts:37`),
  which depends on no owner-line session. That is what lets the MCP server and Ask BIS run the same reads later
  from a Clerk session, with the Technician refusal at THEIR context construction.

### 3.4 The shared chat tool turn

`lib/ai/tool-turn.ts`: `completeWithTool({ db, input, offered, run, budget })`, the web chat's D-047 loop made
general: one completion with the offered tools; if it calls one, run it through `runOffered`, discard any words
written before the result, and ask a second completion with the real result and `toolChoice: "none"` inside what is
left of the budget (`aiOverheadMs` subtracted); too little time or a failure → no second reply, the caller's own
fallback line. At most ONE tool call per turn (today's rule). The chat's capture handler keeps `fileLead`, the
held-without-contact rule, the lost-race re-read and `CaptureOutcome`; the route keeps its fallback lines.

### 3.5 Prompts name only offered tools

`lib/voice/system-prompt.ts`, `lib/voice/knowledge/prompt-blocks.ts` (`transferToolLineClosed`, the `AFTER_HOURS_*`
constants) and the trade modules (`modules/events.ts`, `modules/insurance-pc.ts`) name tools in prose; tool RESULT
text in `call-state.ts` and `identity/*` also names tools but is written by tools that are on the session, so it
stays. The belt adds `offeredSet(session)`, and
every tool-naming line is written through a helper that leaves the line out when the tool is not offered. The
phone's prompt must come out BYTE-IDENTICAL for every mode × meeting type × handoff × trade module × language (a
snapshot test written before the change); the two demos' prompts must name no tool at all.

### 3.6 Out of scope

Chat booking (F-036); merging the two `capture_lead` schemas or save paths; the MCP server, Ask BIS (S-18) and S-33;
any `mcpShape` (added with the MCP server, a three-field mapping); tools on the browser demos (`web-demo.ts:7-12`
explains why they have none).

## 5. Risks and how each is caught

| Risk | Caught by |
|---|---|
| A phone session's tools change by a character | PR 2's fixture from main, every combination |
| A model calling an unoffered tool hears different words | `notOffered` returns today's sentences; registry tests |
| A staff tool reaches a customer session | audience types + the no-shared-name test + owner `session-config.test.ts:19-27` |
| The chat files a lead twice or says "passed on" before filing | PR 3's tool-turn tests + unchanged concierge tests |
| Phone prompt drifts | PR 4's snapshots written before the change |
| `lookup_customer` leaks another account or a Technician-hidden customer | Task 17's privacy tests + reviewer's second-account probe |
| Error logs quote a customer | `runOffered` hands `onError` the class only; the owner line logs that. The phone still rethrows the original error and `call-events.ts` logs `String(err)` as before (PR 2 keeps behaviour); class-only phone logging is a follow-up |
